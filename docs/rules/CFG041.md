# CFG041 — `permissions.deny` does not restrict access to `.env` files

**Severity:** `error` · `warn` (the deny list guards no secret file yet)
**OWASP:** [LLM02:2026 – Sensitive Information Disclosure](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM02_SensitiveInformationDisclosure.md)
**Agents:** claude-code

## What cfgaudit checks

`.env` files routinely hold database passwords, API keys, and other credentials. `permissions.deny` is Claude Code's documented, harness-enforced mechanism for blocking file access. cfgaudit flags a `permissions.deny` block that **exists** but contains **no** pattern covering `.env` files.

A pattern counts as sufficient coverage if it targets `.env`:

```text
.env
.env.*
*.env
**/.env
**/.env.*
```

A completely **absent** `permissions.deny` block is reported by CFG006, not here.

A **deny-all** entry also counts as coverage and suppresses this finding: `Read(*)` / `Read(**)` / `Read(**/*)` (blocks every read, any version), or the bare `"*"` deny-all-tools glob — but `"*"` only on Claude Code **≥ 2.1.166**, where that glob was introduced. On older releases `"*"` is an unknown tool name and a no-op, so the finding still fires (add an explicit `.env` pattern or upgrade). When the Claude Code version is unknown, `"*"` is treated as covering.

An **exception** rule — `Read(!<glob>)` or `Read(./!<glob>)` (also under `Edit` and, for cfgaudit, any tool) — denies nothing; it *removes* the paths it matches from the deny rules listed before it. cfgaudit therefore does not count an exception as coverage, and it un-covers the class when the exception re-exposes the secret: a deny-all with `Read(!**/.env)` after it leaves `.env` readable, so the finding fires. A narrower carve that names a safe sibling, such as `Read(!**/.env.example)` beside a `Read(**/.env*)` deny, does not un-cover `.env` and stays quiet.

## Severity (#1172)

`error` when the deny list already guards secret files (a `Read`, `Edit`, `Grep` or `Glob` rule on a credential path, or the bare tool) and misses this class, and in `auto` or `bypassPermissions` mode, where nothing else stops a read. `warn` when the deny list guards no secret file at all, because it was written for something else, such as blocking `git push`: without any deny list the file would get only one CFG006 warning, and adding an unrelated deny entry should not turn that into three or four errors. In the pre-release corpus run for v1.20.0 on 10,034 repositories, 65 of the 110 settings files these rules reported were of that kind.

## Trigger example

```json path=.claude/settings.json
{
  "permissions": {
    "deny": ["Bash(rm *)"]
  }
}
```

→ `error` (deny exists but no `.env` coverage).

## Safe alternative

```json
{
  "permissions": {
    "deny": ["Read(**/.env)", "Read(**/.env.*)"]
  }
}
```
