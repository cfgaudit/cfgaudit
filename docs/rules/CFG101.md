# CFG101 — a deny rule constrains bundled short flags, which reordering walks past

**Severity:** `warn`
**OWASP:** [LLM06:2025 – Excessive Agency](https://owasp.org/www-project-top-10-for-large-language-model-applications/2025/LLM06_2025-Excessive_Agency.html)

## What cfgaudit checks

Claude Code matches a `Bash(...)` permission pattern as a **literal prefix**. A rule that names flags is therefore evaded by writing the same flags differently. Measured against 2.1.231 in [#480](https://github.com/cfgaudit/cfgaudit/issues/480), with `Bash(echo -n *)` denied:

| Command | Result |
|---|---|
| `echo -n zzAAA` | DENIED |
| `echo -e -n zzBBB` | ran |
| `echo zzCCC -n` | ran |

Applied to the shape this rule reports: **`Bash(rm -rf *)` never covered `rm -fr x`.** Upstream says the same in its own words, calling argument-constrained Bash patterns *"fragile"*.

cfgaudit reports a `deny` or `ask` entry whose pattern contains a **bundled short-flag token** — two or three lowercase letters behind one dash, such as `-rf`, `-fr`, `-it`, `-xzf`. Those are the tokens the shell treats as a set, so writing them in one order does not cover the others. The message names a spelling that reaches the same command.

`allow` rules are not examined. An allow rule that fails to match produces a prompt, which is the safe direction.

## Why it is exactly this narrow

Every exclusion is here because something real would otherwise be misread:

| Shape | Why it is not reported |
|---|---|
| `--force` | a long flag cannot be permuted within itself |
| `-f` | a lone short flag has nothing to permute |
| `find -name`, `find -type`, `java -version` | four or more letters behind one dash is where single-dash **long options** live in real tools. Permuting their letters produces nonsense |
| `PowerShell(Remove-Item -Recurse)` | PowerShell writes every parameter as a single `-Word` and does not bundle at all, so the evasion does not exist there |
| `npm run test` | a subcommand is not a flag and does not reorder freely |
| `Bash(*)` | a catch-all constrains no arguments |

**A file that also denies the bare command is not reported.** `Bash(rm -rf *)` beside `Bash(rm *)` leaves no gap: the broad rule catches every spelling and the narrow one is redundant rather than a hole.

## The remedy is always available for the reported shape

Deny the command by name:

```json
{ "permissions": { "deny": ["Bash(rm *)"] } }
```

That is what [#482](https://github.com/cfgaudit/cfgaudit/pull/482) did to this project's own `cfgaudit init` baseline, replacing `Bash(rm -rf *)` with `Bash(rm *)`. Widening a deny rule is safe in a way that widening an allow rule is not.

For shapes this rule does **not** report, such as force-push, no broader form exists that would not block every push. Those stay guidance, and upstream points at OS-level sandboxing and `PreToolUse` hooks for the part a pattern cannot enforce.

## Footprint

Across **141 real `.claude/settings.json` files** carrying a deny list, **26 (18%) leave the gap open**, for 49 findings. Almost all are `Bash(rm -rf …)`.

The rate is high and the finding is not noise. Three repositories in that sample write **both** `Bash(rm -rf …)` and `Bash(rm -fr …)`, so their authors already know the ordering matters and enumerated around it — and still miss `-r -f`. Only one file in the whole sample also carries the bare `Bash(rm *)` that would close it.

This is the distinction that separates this rule from findings this project has declined at similar rates. [#459](https://github.com/cfgaudit/cfgaudit/pull/459) dropped CFG095's build-cache warn, and CFG089's escalation and the Cursor `environment.json` routing were both declined, because in each case the population was **documented normal usage**. Here the population is **attempted protection that does not work**, which is what a config linter exists to say.

## Trigger example

```json
{ "permissions": { "deny": ["Bash(rm -rf *)"] } }
```

→ `warn`: `rm -fr` reaches the same command.
