# CFG025 — custom organisation policy (require-deny / forbid-allow)

**Severity:** `error`
**OWASP:** [LLM03:2026 – Excessive Agency](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM03_ExcessiveAgency.md)
**Agents:** antigravity, claude-code, codex, cursor, devin, gemini-cli, grok, kilo-code, opencode, qwen-code, roo-code, vscode

## What cfgaudit checks

CFG025 enforces an organisation's **own** permission policy, declared in [`.cfgaudit.yml`](../usage.md#configuration-file-cfgaudityml). Unlike the other rules (which encode universal CVE/hardening checks), CFG025 is **inert until you configure a `policy:` section**. It evaluates against the project's `permissions.allow` / `permissions.deny`.

```yaml
# .cfgaudit.yml
policy:
  # Commands that MUST be blocked by permissions.deny.
  require-deny:
    - "Bash(git commit:*)"
    - "Bash(git push:*)"
  # Commands that MUST NOT be grantable by permissions.allow.
  forbid-allow:
    - "Bash(git commit:*)"
    - "Bash(curl:*)"
```

- **`require-deny`** → `error` when no `permissions.deny` entry **covers** the command. This is the strong guarantee: in Claude Code `deny` beats `allow`, so a covered deny actually blocks it.
- **`forbid-allow`** → `error` when any `permissions.allow` entry **grants** the command (in whole or part).

### Containment-aware matching

Matching is not a plain string compare — broader patterns subsume narrower ones:

| Policy target | `require-deny` satisfied by a deny of | `forbid-allow` violated by an allow of |
|---------------|----------------------------------------|----------------------------------------|
| `Bash(git commit:*)` | `Bash(git commit:*)`, `Bash(git:*)`, `Bash(*)` | `Bash(git commit:*)`, `Bash(git:*)`, `Bash(*)`, or any `Bash(git commit …)` |

So a narrower deny (`Bash(git commit --amend)`) does **not** satisfy `require-deny: Bash(git commit:*)`, while any allow that grants even one `git commit` invocation violates `forbid-allow`.

Evaluated against the **project** `settings.json` (the committed artifact a CI policy applies to).

## Agent-neutral policy

A team that uses more than one agent writes the policy once under `deny` and the mapping form of `forbid-allow`, and CFG025 checks it against each agent's committed permission file (#1081):

```yaml
policy:
  deny:
    commands: ["git push"]          # word prefix: git push, git push origin main
    read: ["**/.env", "~/.ssh/**"]  # paths relative to the repository, or ~/
    write: ["src/generated/**"]
    fetch: ["*.example.com"]        # domains; *. for every subdomain
    mcp-tools: ["github:delete_*"]  # server:tool; the tool may be * or end in *
  forbid-allow:
    commands: ["curl"]
    mcp-tools: ["github:*"]
  agents: [claude-code, devin]      # optional
```

Without `agents`, the policy applies to every agent with configuration in the repository: Claude Code when `.claude/`, `CLAUDE.md` or `.mcp.json` exists, Devin CLI when `.devin/` exists, Cursor CLI when `.cursor/cli.json` exists, Qwen Code when `.qwen/` or `QWEN.md` exists, Grok when `.grok/` exists, OpenCode when `.opencode/`, `opencode.json` or `opencode.jsonc` exists, Kilo Code when `.kilo/`, `.kilocode/`, `kilo.json` or `kilo.jsonc` exists, Codex when `.codex/` exists, Roo Code when `.roo/`, `.roomodes`, `.roorules` or `.rooignore` exists, Gemini CLI when `.gemini/` or `GEMINI.md` exists, pi when `.pi/` exists, Cursor when `.cursor/permissions.json` or `.cursor/sandbox.json` exists, VS Code when `.vscode/settings.json` sets a `chat.tools` auto-approve key. `.cursor/` alone can be Cursor CLI, and most `.vscode/` directories have nothing to do with the agent. An agent named under `agents` is checked even when it has no configuration yet, so a missing file is reported rather than skipped. Agents that read their permission rules from user settings only (Zed, Continue) get one [CFG118](CFG118.md) info finding instead. Any other name is rejected with exit 2 until cfgaudit can check that agent.

A missing deny is reported against the agent's file with the entry to add, in that agent's syntax:

| Category | Claude Code (`.claude/settings.json`) | Devin CLI (`.devin/config.json`) |
| --- | --- | --- |
| commands | `Bash(git push *)`; also covered by `Bash(git:*)`, `Bash(*)`, `Bash` | `Exec(git push)`; also covered by `Exec(git)`, `exec` |
| read | `Read(**/.env)`; also covered by `Read(.env)`, `Read(dir/**)`, `Read` | `Read(**/.env)`; also covered by `Read(dir/**)`, `read` |
| write | `Edit(src/generated/**)`; a `Read` deny of the path covers it too | `Write(src/generated/**)`; also covered by `edit` |
| fetch | `WebFetch(domain:*.example.com)`; also covered by `WebFetch(domain:*)`, `WebFetch` | `Fetch(https://*.example.com/*)`, or `Fetch(domain:example.com)` for one domain |
| mcp-tools | `mcp__github__delete_*`; also covered by `mcp__github`, `mcp__github__*`, `mcp__*` | `mcp__github__delete_*`; also covered by `mcp__github__*`, `mcp__*` |

Cursor CLI (`.cursor/cli.json`) is checked as the code of its package 2026.11.05-86047df behaves, read but not run, which differs from its documentation in two places:

| Category | Entry to add | Also covered by | Not covered by |
| --- | --- | --- | --- |
| commands | `Shell(git push)` | `Shell(git)`, `Shell(git:*)`, `Shell(git:push*)`, `Shell(*)`, and the same with `Bash(...)` | `Shell(git push *)` and `Shell(git:push)`, which let a bare `git push` or `git push origin` run |
| read | `Read(**/.env)` | `Read(**)`, `Read(**/.env*)` | `Read(.env)`, `Read(.env*)` and `Read(src/**)`: the CLI compares a pattern with the whole absolute path, so a relative pattern never matches, although its documentation shows `Read(.env*)` |
| write | `Write(**/src/generated/**)` | `Write(**)`, `Write(**/src/**)` | `Read(...)`: a Read deny does not block writes |
| mcp-tools | `Mcp(github:delete_*)` | `Mcp(github:*)`, `Mcp(*:*)`; case does not matter | |

Cursor CLI also adds `permissions` from `.claude/settings.json`, so a deny there counts when the CLI reads it the same way, and an allow there counts for `forbid-allow`. `deny.fetch` is not checked for it: a `WebFetch` deny only decides whether approval can be skipped, so [CFG118](CFG118.md) reports the category instead. A `.cursor/cli.json` in a subdirectory replaces the lists of the one above it when the CLI starts below it, and the root file replaces the user's lists; cfgaudit checks the root file only.

Qwen Code (`.qwen/settings.json`) and Grok (`.grok/config.toml`) are checked as their source behaves (qwen-code c2e77d1, grok-build 2bdd1d6):

| Category | Qwen Code | Grok |
| --- | --- | --- |
| commands | `Bash(git push)`; also `Bash(git push *)`, `Bash(git:*)`, `Bash`. `Shell(...)` works too | `Bash(git push)`; also `Bash(git *)`, `Bash(git:*)`, `Bash`. Not `Bash(git push *)`, which misses a bare `git push` |
| read | `Read(**/.env)`; also `Read(dir/**)`, `Read`. Not `Read(.env)`, one file | `Read(**/.env)`, and `Read(**/.ssh/**)` for `~/.ssh/**`: Grok keeps a leading `~/` as literal text |
| write | `Edit(/src/generated/**)`; also `Edit`. Not `Write(...)`, which skips the edit tool | `Edit(src/generated/**)` or `Write(...)`, one tool in Grok |
| fetch | `WebFetch(domain:example.com)`; also `WebFetch(example.com)`, `WebFetch` | `WebFetch(domain:example.com)`, `WebFetch`; a `*.` pattern matches nothing |
| mcp-tools | `mcp__github__delete_*`; also `mcp__github`, `mcp__*` | `MCPTool(github__delete_*)`; also `mcp__github`, `mcp__*`, `MCPTool` |

Both have no rule for subdomains alone, so `*.example.com` asks for the rule on `example.com`, which also blocks that host. Qwen's legacy `tools.exclude` counts as deny. Grok's structured `rules` count unless a compact `allow`, `deny` or `ask` array is set, because Grok then ignores them. Grok also adds `permissions` from `.claude/settings.json`, like Cursor CLI, and that includes `allow`, so `forbid-allow` looks there too. Grok ignores project rules in an untrusted folder; Qwen Code applies them unless folder trust is turned on.

OpenCode and Kilo Code resolve rules by the **last matching rule**, in file order, so a list is not read as a set. CFG025 asks what concrete requests resolve to, for the top-level `permission` block and again with each `agent.<name>.permission` block after it, because a later allow reopens an earlier deny.

| Category | Rule to add | Notes |
| --- | --- | --- |
| commands | `"git push *": "deny"` under `bash` | a trailing ` *` also matches a bare `git push`; `"git push"` alone is exact |
| read | `"*.env": "deny"` under `read` for `**/.env` | `**/.env` matches no file at the root, because the pattern needs a slash; a repository path stays `src/**` |
| write | `"src/generated/*": "deny"` under `edit` | `edit` covers edit, write and patch |
| home paths | `"~/.ssh/**": "deny"` under `external_directory` | a path outside the project goes through this permission, not `read` |
| fetch | OpenCode: see [CFG118](CFG118.md). Kilo Code: `"*://*.example.com/*": "deny"` under `webfetch` | OpenCode applies `webfetch` to all URLs |
| mcp-tools | `"github_delete_*": "deny"` | the permission key is `server_tool` |

Files are read in the agent's order and their rules concatenated. Both agents deep-merge them instead, so a key a later file repeats keeps its first position; cfgaudit does not model that, and a rule in an agent's Markdown file is not read here. OpenCode has no workspace trust step, so a committed rule applies as soon as it runs; Kilo Code was not measured on this.

Codex has no single permission list, so each category lives somewhere else:

| Category | Where | Entry |
| --- | --- | --- |
| commands | a `.rules` file in `.codex/rules/` | `prefix_rule(pattern=["git", "push"], decision="forbidden")`. Tokens match exactly and in order, and the strictest match wins, so a forbidden rule beats any allow |
| read | the selected permission profile | `"**/.env" = "deny"` under `[permissions.<profile>.filesystem.":workspace_roots"]`; `"~/.ssh" = "deny"` under `[permissions.<profile>.filesystem]` |
| write | the same | `"src/generated/**" = "read"`, or `deny` |
| fetch | the same | `"*.example.com" = "deny"` under `[permissions.<profile>.network.domains]`; `enabled = false` also covers it |
| mcp-tools | `[mcp_servers.<server>]` | `disabled_tools`, exact names only, or an `enabled_tools` list without the tool, or `enabled = false` |

A profile only counts through `default_permissions`, and CFG025 follows its `extends` chain within the file. Without one, a path or fetch entry asks for a profile, because a built-in profile cannot carry a deny. A `prefix_rule` built from Starlark variables is not read. An MCP entry for a server the file does not configure is skipped: Codex has no rule for a server by name, and a table for it needs a transport. Codex validates the `match` and `not_match` examples of a rule when it loads the file, and a failing example rejects the file, which cfgaudit does not check. Codex ignores project files in an untrusted folder.

Roo Code keeps these in three places:

| Category | Where | Entry |
| --- | --- | --- |
| commands | `.vscode/settings.json` | a prefix in `roo-cline.deniedCommands`. It wins unless `roo-cline.allowedCommands` has a longer prefix. Prefixes have no word boundary and ignore case |
| read, write | `.rooignore` | a gitignore line. Read and write tools check it, but shell commands only for a short list such as `cat`, and paths outside the project are allowed, so a home path goes to [CFG118](CFG118.md) |
| fetch | none | [CFG118](CFG118.md) |
| mcp-tools | `.roo/mcp.json` | `disabledTools`, exact names, or `disabled: true` |

Roo Code consults its command lists only when the user's auto-execute setting is on; with it off, every command asks, and a user can still approve a denied one.

Gemini CLI and pi can only switch a whole tool off, with `tools.exclude` or a `tools.core` list, and `defaultTools`. Turning off `run_shell_command` covers every command entry, so CFG025 reports nothing there, and [CFG118](CFG118.md) reports the categories still open. `tools.allowed` counts for the neutral `forbid-allow.commands`.

Cursor (`cursor`, the editor) and VS Code have allowlists only, so CFG025 checks `forbid-allow` and [CFG118](CFG118.md) reports `deny`:

- **Cursor:** `terminalAllowlist` and `mcpAllowlist` in `.cursor/permissions.json`, read as Cursor reads `Shell(...)` and `Mcp(...)` tokens. `.cursor/sandbox.json` does not count for `deny.read` or `deny.fetch`: it limits sandboxed commands, not the agent's tool calls.
- **VS Code:** `chat.tools.terminal.autoApprove`. A plain key is a word prefix, and a `false` entry keeps the prompt for what it covers. A `/regex/` key is tried on the command with and without arguments; one that cannot be read gives a `warn`, because the overlap is undecidable. VS Code has no committed list for MCP tools, so `forbid-allow.mcp-tools` is not checked.

## Rulesync

A team that generates its agent files with [Rulesync](https://github.com/dyoshikawa/rulesync) already has a neutral source. `rulesync: true` under `policy` adds `.rulesync/permissions.jsonc`, or the legacy `.rulesync/permissions.json`, to the policy, and CFG025 then checks that the committed agent files enforce it (#1519):

```yaml
policy:
  rulesync: true
```

- `deny` rules become required denies: `bash` a command, `read`, `edit` and `write` a path, `webfetch` a domain, and `mcp__server__tool` an MCP entry. A trailing ` *` or `:*` goes, and a path stays as written: Rulesync passes `.env` to each tool unchanged, and the tools read a bare name differently, so write `**/.env` if every depth is meant.
- A tool's own block (`claudecode.permission`, `codexcli.permission`) replaces the shared category for that agent.
- `ask` rules for `bash` and MCP tools become `forbid-allow`, so an agent file that turns them into `allow` is reported. `allow` rules constrain nothing.
- With `.cfgaudit.yml` entries as well, both apply. A deny there that the Rulesync file allows is a CFG025 finding on the Rulesync file.
- A rule with no neutral form, such as `"*": "deny"` under `bash` or a glob inside a command, is listed by [CFG118](CFG118.md) and not checked.

Which agents are checked does not change: `agents`, or every agent with configuration in the repository. `targets` in `rulesync.jsonc` is not read, so an agent cannot drop out of the check because it is missing there.

The option is off by default, so a project that uses Rulesync does not start failing on rules nobody asked cfgaudit to enforce.

For example, with this policy and no `.claude/settings.json` yet:

```yaml path=.cfgaudit.yml
policy:
  deny:
    commands: ["git push"]
  agents: [claude-code]
```

```text
.claude/settings.json [error] CFG025: policy deny.commands "git push": no permissions.deny entry covers it, so Claude Code does not block it; add "Bash(git push *)"
```

The neutral `forbid-allow` takes `commands` and `mcp-tools` only: whether an allowed path glob overlaps a forbidden one cannot be decided from the two strings. Claude Code skips an allow entry of `mcp__*`, so it does not count as granting a tool.

A deny in a committed file is a team default, not a guarantee: Claude Code and Devin CLI merge it with each contributor's own settings, Cursor CLI lets a nested `.cursor/cli.json` replace it, and a contributor can run the agent in a mode that skips prompts. The policy tells you the committed files say what the team agreed on.

## Example: "Claude may never run commit/push"

```yaml
policy:
  require-deny: ["Bash(git commit:*)", "Bash(git push:*)"]
  forbid-allow: ["Bash(git commit:*)", "Bash(git push:*)"]
```

## Limitation

Path globs are compared as strings: an entry covers a path when it is the same glob, `**`, or `dir/**` for a path below `dir`. A deny that covers the path in some other way is reported as missing, and the message names the entry that satisfies the check. For the Claude Code lists, matching covers the common Claude Code permission shapes (`Tool(cmd)`, `Tool(cmd:*)`, `Tool(cmd *)`, `Tool(*)`). Exotic glob forms inside the body are not interpreted.
