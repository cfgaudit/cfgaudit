# CFG052 — mcpServers in a Claude Code settings.json has no effect

**Severity:** `info`
**OWASP:** [LLM04:2026 – Supply Chain](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM04_SupplyChain.md)
**Agents:** claude-code

## What cfgaudit checks

An `mcpServers` block in `.claude/settings.json`, `.claude/settings.local.json` or `~/.claude/settings.json` is not read by Claude Code. Its MCP servers come from the project's `.mcp.json`, from `~/.claude.json` (where `claude mcp add` writes) and from plugins. A developer who defines a server in `settings.json` probably expects it to start, and it does not. cfgaudit reports the block once, at `info`.

The other MCP rules still read the block: a secret or an unpinned package in it is committed and public whether or not Claude Code uses it.

## Why it changed (#1215)

CFG052 used to report a server name declared both in `settings.json` and in `.mcp.json` as a shadowing conflict, at `warn`. Measured on Claude Code 2.1.316 in a project that defines `probe-settings` only in `.claude/settings.json` and `probe-mcpjson` only in `.mcp.json`:

- `claude mcp list` shows `probe-mcpjson` (pending approval) and not `probe-settings`;
- `claude mcp get probe-settings` answers `No MCP server named "probe-settings"`;
- the settings reference has no `mcpServers` key.

There is no second source, so there is no precedence conflict. Gemini CLI and Qwen Code do read `mcpServers` in their own `settings.json`; those files are not this rule's subject.

## Trigger example

`.claude/settings.json`:

```json
{ "mcpServers": { "github": { "command": "npx", "args": ["-y", "gh-mcp"] } } }
```

→ `info`: mcpServers in a Claude Code settings.json has no effect.

## Safe alternative

Move the servers to `.mcp.json` for project-shared servers, or add them with `claude mcp add` for personal ones, and remove the block from `settings.json`.
