# CFG051 — skill/command/subagent grants overly broad `allowed-tools`

**Severity:** `error` (all-tools `*`/`all`) · `warn` (unrestricted shell `Bash`) · `info` (a skill root whose readers were not measured, or a shell tool name Claude Code does not have)
**OWASP:** [LLM03:2026 – Excessive Agency](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM03_ExcessiveAgency.md)
**Agents:** amp, claude-code, cline, codex, continue, copilot, crush, cursor, devin, devin-desktop, gemini-cli, goose, grok, kimi-code, opencode, openhands, qwen-code, vscode, zed

## What cfgaudit checks

Claude Code custom **slash commands** (`.claude/commands/**/*.md`), **subagents** (`.claude/agents/*.md`), and plugin **skills** (`SKILL.md`) declare which tools they may use in a YAML frontmatter `allowed-tools` field. A committed command/skill that grants unrestricted shell or all tools can run anything the moment it is invoked — the frontmatter analogue of the permission-breadth rules (CFG002/CFG006).

cfgaudit parses the frontmatter and flags an `allowed-tools` grant that is too broad:

| Grant | Result |
|-------|--------|
| `*`, `all`, `full` | `error` — unrestricted tool access |
| `Bash` (bare, no `Bash(cmd)` restriction), `Bash(*)` and other wildcard-only scopes such as `Bash(**)` and `Bash(* *)`, `shell`, `execute`, Devin's `exec` | `warn` — unrestricted shell access (broad but commonly legitimate) |

A grant that is cancelled by a sibling `disallowed-tools` entry is not flagged. An unclosed parenthesis stays inside its `disallowed-tools` entry, so `Bash(rm *` does not cancel a `*` grant. A scoped grant such as `Bash(npm test)` or a specific tool list (`Read`, `Edit`) is fine. A scoped grant may contain spaces and wildcards next to a command, as in `Bash(git -C * status)`: the wildcard stays inside the scope. Files without `allowed-tools` frontmatter (plain CLAUDE.md, `.cursorrules`, …) produce no finding.

**Gemini CLI skills (#1153).** Gemini CLI does not read `allowed-tools`, so the field grants nothing to a skill it loads from `.gemini/skills` (project or user scope), and such a skill is not reported. The same file under `.claude/skills` or another root whose agent honours the field still is. `.qwen/skills` stays in scope until Qwen Code, which forked Gemini CLI's skill loader, is measured.

### Which agents honour the field (#1196)

Measured with a skill whose body runs `touch`, once without `allowed-tools` as a baseline and once with `allowed-tools: Bash`:

| Agent | Skill roots | `allowed-tools` grants the command? |
| --- | --- | --- |
| Claude Code 2.1.316 | `.claude/skills`, plugins | yes for `Bash`; no for `bash`, `shell` or `execute` (case-sensitive tool names) |
| Copilot CLI 1.0.95 | `.github/skills`, `.agents/skills`, `.claude/skills` | no, also with `shell` and `shell(touch)` |
| OpenCode 1.18.18 | `.agents/skills`, `.opencode/skills`, `.claude/skills` | no: with `bash` set to `ask`, the command is still asked about |
| Codex, Cursor, Qwen Code | `.agents/skills`, `.codex/`, `.cursor/skills`, `.qwen/skills` | not measured (not signed in or not installed) |

So:

- `.github/skills` and `.opencode/skills` are not reported: the agents that read them do not treat the field as a grant, like `.gemini/skills` (#1153).
- `.agents/skills`, `.codex/` and `.cursor/skills` are reported at `info`: Claude Code does not read them, the measured readers ignore the field, and Codex and Cursor are open.
- In a root Claude Code reads, a shell grant spelled `bash`, `shell` or `execute` is `info`: it grants nothing, since the tool is named `Bash`.

Byte-identical copies of a skill in several roots are still reported once per file.

## Trigger example

```markdown path=.claude/skills/deploy/SKILL.md
---
description: Deploy the app
allowed-tools: Bash, Read
---
Run the deploy script.
```

→ `warn` (bare `Bash` = unrestricted shell; broad but often legitimate). Narrow it when you can:

```markdown
---
description: Deploy the app
allowed-tools: Bash(./deploy.sh), Read
---
```

## Safe alternative

Grant only the specific tools (and specific Bash commands) the command needs, or use `disallowed-tools` to remove dangerous ones from a broader set.

## Devin

Devin CLI skills name tools in lower case (`read`, `edit`, `grep`, `glob`, `exec`), and its skill reference says `allowed-tools` entries are "auto-approved (no permission prompt) while the skill runs", so a bare `exec` is reported like a bare `Bash`. A Devin custom subagent profile (`.devin/agents/`) is not checked: there `allowed-tools` "restricts the tool set", the opposite of a grant.
