# CFG118: a policy deny cannot be committed for an agent

**Severity:** `info`
**OWASP:** [LLM03:2026 – Excessive Agency](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM03_ExcessiveAgency.md)
**Agents:** zed, continue, goose, kimi-cli, cline, cursor

## What cfgaudit checks

CFG118 is inert until `.cfgaudit.yml` sets the agent-neutral `policy.deny` described in [CFG025](CFG025.md). It then reports, once per agent, an agent in the policy's scope that has no committed permission file, so no entry in the repository can carry the deny for it:

| Agent | Marked by | Where its permission rules live |
| --- | --- | --- |
| Zed | `.zed/` | user `settings.json`; the project `.zed/settings.json` has no `agent` section |
| Continue | `.continue/` | the user's `~/.continue/` permissions |
| goose | `.goose/`, `.goosehints` | per-tool permissions in the user's `permission.yaml` |
| Kimi CLI | `.kimi/` | no deny list; `PreToolUse` hooks in the user's `~/.kimi/config.toml` |
| Cline | `.cline/`, `.clinerules` | no allow or deny list; a `PreToolUse` hook under `.cline/hooks/` can block calls, and `.clineignore` is documented as no security boundary |

An agent is in scope when one of these paths exists in the repository, or when `policy.agents` names it.

Cursor CLI has a committed permission file, so [CFG025](CFG025.md) checks it, but `deny.fetch` is reported here. The code of package 2026.11.05-86047df consults a `WebFetch` deny only to decide whether approval can be skipped; the approval step reads the allow list alone, so a user or an allow entry can still approve the fetch.

## Trigger example

```yaml path=.cfgaudit.yml
policy:
  deny:
    commands: ["git push"]
    read: ["**/.env"]
  agents: [zed]
```

The same finding appears without `agents` when the repository has a `.zed/` directory:

```text
.zed [info] CFG118: policy deny.commands, deny.read cannot be enforced for Zed from a permission file in the repository: Zed reads its permission rules from user settings only, so each contributor has to add the rules to their own settings
```

## Why it is info

Nothing in the repository is wrong. The finding keeps a policy from reading as if it covered every agent the team uses: for these agents each contributor has to add the rules to their own settings, or for Cline the team has to commit a hook, and a reviewer should know that. It shows in SARIF and GitLab Code Quality and never fails CI on its own.

## Fix

Ask contributors who use the agent to add the rules to their user settings, commit a `PreToolUse` hook for Cline, or list only the agents the policy is meant to cover under `policy.agents`. Turn the rule off with `rules: {CFG118: off}` if the team already knows.
