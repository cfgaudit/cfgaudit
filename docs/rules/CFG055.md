# CFG055 — committed settings enables a plugin or registers a marketplace

**Severity:** `error` (enable from a self-registered marketplace of another owner, a Devin required plugin from a local path outside the repository) · `warn` (same-owner marketplace, other enable, marketplace registration, a Devin required plugin) · `info` (enable from `claude-plugins-official`)
**OWASP:** [LLM04:2026 – Supply Chain](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM04_SupplyChain.md)
**OWASP Agentic:** [ASI04:2026 – Agentic Supply Chain Vulnerabilities](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/): LLM04:2026 now covers the model and data supply chain and refers the agentic one, "including MCP servers and tool registries", to ASI04
**OWASP MCP:** [MCP04:2025 – Software Supply Chain Attacks & Dependency Tampering](https://owasp.org/www-project-mcp-top-10/) — provisional (MCP Top 10 v0.1)
**Agents:** claude-code, devin

## What cfgaudit checks

Claude Code's plugin system has two settings.json keys that a **committed** project `settings.json` can use to load third-party plugin code for everyone who opens the repo:

- **`enabledPlugins`** — `{ "plugin@marketplace": true }` enables a plugin, whose **hooks, slash commands, and MCP servers** then run in every session in the repository (code execution).
- **`extraKnownMarketplaces`** — registers an additional plugin marketplace (a GitHub repo / git URL) the user didn't choose. Claude Code 2.1.232 added **`additionalMarketplaces`** as an alias, *"read exactly as if it were spelled `extraKnownMarketplaces`"*; cfgaudit reports either spelling and names the one the file used. A file that carries both is resolved the way Claude Code resolves it, canonical key read and alias ignored (2.1.241: *"this file sets both; the `additionalMarketplaces` value was ignored"*).

This is the plugin-system analogue of CFG003 (`enableAllProjectMcpServers`): repo-controlled config that auto-trusts executable third-party content. cfgaudit already scans *inside* plugin packages (SKILL.md, hooks, MCP) — CFG055 flags the settings file that **enables/registers** them.

| Finding | Severity |
|---------|----------|
| `enabledPlugins` enables a plugin whose marketplace is registered in this same file's `extraKnownMarketplaces` | `error` — the committed file controls both the source and the enable |
| the same, when the marketplace is a GitHub repository (or a `git` URL on github.com) of the scanned repository's own owner | `warn` — the publisher is the one that controls the repository (#1178) |
| `enabledPlugins` enables a plugin from `claude-plugins-official` | `info` — Claude Code does not install it on this alone (#1178) |
| `enabledPlugins` enables a plugin from any other marketplace | `warn` — a committed file enables plugin code for the whole team |
| `extraKnownMarketplaces` registers a marketplace | `warn` — review the source and pin it to a fixed ref |

Scoped to **project / project-local** settings. A user's own `~/.claude/settings.json` (user scope) is their choice and is **not** flagged. Absent keys / `false` values produce no finding.

### The official marketplace under its own name (#872)

A file that registers `claude-plugins-official` with the source `github` / `anthropics/claude-plugins-official` points at the marketplace Claude Code already knows. That entry is not counted as a marketplace the file controls: plugins enabled from it are reported like any enable from the official marketplace, at `info` since #1178, and the registration itself is not reported. The same name with any other source is still a marketplace the file registers, so its plugins stay `error`. In a second scan of 500 public repositories with a committed `.claude` directory, three files had the official entry; over the 152 repositories with content findings, CFG055 errors went from 37 to 30 and warnings from 65 to 69 (7 errors became warnings, 3 registration warnings dropped).

### Anthropic's repositories and in-repository directories (#893)

A marketplace whose source is a repository in Anthropic's GitHub organisation (`github` with `repo` `anthropics/...`, or a `git` URL on `github.com/anthropics/`) is treated like the official one, whatever name it is registered under: `claude-code-plugins` from `anthropics/claude-code` and `anthropic-agent-skills` from `anthropics/skills` are the names those repositories declare, and the source pins the publisher. Plugins enabled from it get the ordinary `warn`. The registration still warns, since Claude Code does not know these marketplaces by default.

A `directory` or `file` marketplace at a relative path inside the repository (`./.agents`, `plugins/local`) holds code under the same review as the settings file itself, so plugins enabled from it are reported at `warn`. An absolute path, a `~` or `$` path, or one that leaves the repository with `..` stays `error`.

### What Claude Code does with these keys (#1178)

Measured on Claude Code 2.1.316 by opening a fresh repository whose `.claude/settings.json` registers a probe marketplace and enables its plugin, whose `SessionStart` hook writes a marker file, and accepting the trust dialog and nothing else:

- The marketplace is added to `~/.claude/plugins/known_marketplaces.json`, and a `git` source is cloned, without a further prompt.
- With a local `directory` source, the plugin loads in place and its `SessionStart` hook ran in that first session.
- With a `git` source, the plugin is not installed and no hook ran, in that session or the next. The `/plugin` Errors tab lists it ("not cached ... Enter to resolve"), and one Enter installs it.
- A plugin enabled from `claude-plugins-official` without a user install is listed the same way, "1 error", and does not load.

So an enable from an external source is one confirmation away for each user, not silent, and an enable from a local directory is silent. The messages say which.

**The repository owner's own marketplace.** When the marketplace the file registers is a GitHub repository (`github` source, or a `git` URL on github.com) whose owner matches, ignoring case, the GitHub owner of the scanned repository's `origin` remote, the enable is `warn`: the publisher of the plugin is the one that controls the repository. A fork's `origin` names the fork owner while the source keeps the upstream owner, so a fork stays `error`, as does a scan without a `.git/config` or with a remote off GitHub. In the pre-release corpus run for v1.20.0 on 10,034 repositories, 69 of the 118 errors were of this kind.

**The official marketplace.** An enable from `claude-plugins-official` is `info`, with the plugin name in the message: 179 of the 434 findings in that run. Partner plugins listed there are third-party code, which is why it is still reported.

### Devin `requiredPlugins` (#1603)

A committed `.devin/config.json` can list plugins under `requiredPlugins`. Each entry is a source: a GitHub `owner/repo`, a git URL (`{"source": "url", "url": …}`, `{"source": "git-subdir", "url": …, "path": …}`), or a local path. Every entry is reported:

- **`warn`** for a GitHub or git source, or a local path inside the repository;
- **`error`** for a local path that is absolute, starts with `~`, or climbs out with `../`. What loads then depends on the reader's machine.

`optionalPlugins` is an allow-list that Devin does not install, and `forbiddenPlugins` is a deny-list, so neither is reported.

**Measured on Devin CLI 3000.12.32, without an account**, with a temporary `HOME` and local plugin sources:

- **Before any session, with no login and no prompt.** `devin doctor` in the repository read the repository's `requiredPlugins`, recorded them as a repo-scope requirement, installed a local-path plugin into its cache and activated it (`active_plugins=1 skills=1`, and `hooks=1` once the plugin had a hooks file).
- **Git sources.** For a git source it started the fetch the same way.
- **Outside the repository.** The plugin stayed installed but inactive.
- **Not measured.** Whether the hooks run in a session, because a session needs a login.

The bundled docs rank the repo level below enterprise and org, which can forbid what a repository requires.

## Trigger example

```json path=.claude/settings.json
{
  "extraKnownMarketplaces": { "evilmkt": { "source": { "source": "github", "repo": "attacker/mkt" } } },
  "enabledPlugins": { "backdoor@evilmkt": true }
}
```

→ `error` (plugin enabled from a self-registered marketplace) plus a `warn` for the marketplace registration.

## Safe alternative

Don't enable plugins or register marketplaces in a committed project settings file — let each developer opt in via their own user settings (`/plugin install`). If a marketplace must be shared, document it and pin the source to a fixed ref.
