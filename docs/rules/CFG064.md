# CFG064 — Codex CLI sandbox disabled or widened

**Severity:** `error` (sandbox disabled, `network_access`, credential/system/root `writable_roots`) · `warn` (other outside-workspace `writable_roots`)
**OWASP:** [LLM06:2025 – Excessive Agency](https://owasp.org/www-project-top-10-for-large-language-model-applications/2025/LLM06_2025-Excessive_Agency.html)

## What cfgaudit checks

OpenAI Codex CLI's `sandbox_mode` (in `.codex/config.toml`) controls how tool execution is confined. The value **`danger-full-access`** disables the sandbox entirely — tools run with full filesystem and network access — the analog of weakening Claude Code's sandbox (CFG022). Combined with `approval_policy = "never"` (CFG063) it is a fully unattended, unsandboxed agent.

The safe values are `read-only` and `workspace-write`.

## Short of disabling it: the `[sandbox_workspace_write]` table

`workspace-write` is not one posture but a configurable one. The table that tunes it is consulted whenever the effective sandbox mode is workspace-write, and cfgaudit reports the two fields that widen it:

| Field | Finding |
|---|---|
| `network_access = true` | `error` — the workspace-write sandbox otherwise blocks outbound network, so this re-opens an egress path for anything the agent can read |
| `writable_roots` naming a credential dir, system path, home or `/` | `error` |
| `writable_roots` naming anything else outside the workspace | `warn` |

`writable_roots` is judged exactly like Cursor's `additionalReadwritePaths` in [CFG095](CFG095.md), including the workspace root being derived from the config file's own path, so a grant that stays inside the workspace is silent.

### When the table is skipped

Codex reads `[sandbox_workspace_write]` **only** under workspace-write. So:

- `sandbox_mode = "read-only"` → the table is inert, nothing is reported from it.
- `sandbox_mode = "danger-full-access"` → the sandbox is gone entirely; that error is strictly worse than anything in the table, so cfgaudit reports it alone rather than adding noise about settings Codex never reaches.
- **`sandbox_mode` unset** → still reported. Codex resolves an unset mode to workspace-write for a directory carrying a trust decision (`codex-rs/config/src/config_toml.rs`), which is the ordinary project case.

### What is deliberately **not** flagged

`exclude_tmpdir_env_var` and `exclude_slash_tmp` **harden** the sandbox. Codex builds the writable set as *workdir, then `/tmp` unless `exclude_slash_tmp`, then `$TMPDIR` unless `exclude_tmpdir_env_var`* (`codex-rs/utils/sandbox-summary`), so setting either to `true` removes a writable location. The issue that requested this coverage listed both as looseners to bundle; the source says the opposite, and reporting hardening as a weakness would be a false positive — the same trap Cursor's `disableTmpWrite` set in CFG095.

## The second mechanism: named permission profiles

Codex has a richer permission system alongside `approval_policy` and `sandbox_mode`. Two top-level keys drive it: `[permissions]` defines named profiles, and `default_permissions` selects one. Per the schema, a name starting with `:` refers to a built-in profile, any other name is resolved from the `[permissions]` table.

A profile carries `filesystem`, `network`, `workspace_roots` and `extends`. cfgaudit reads the `network` block, which is the sharp end:

| Field | Reported as |
|---|---|
| `proxy_url`, `socks_url` | `error`: routes the agent's traffic through a host the repository chose, which is CFG021's threat model reached through Codex's own config |
| `dangerously_allow_all_unix_sockets` | `error`: reaches the container and service sockets that are equivalent to a root shell |
| `dangerously_allow_non_loopback_proxy` | `error` alongside a proxy URL (it is what makes the remote proxy usable), `warn` on its own |
| `enabled = true` | `error`: flips the effective sandbox from restricted network to enabled network |

Worth stating plainly: the project-layer denylist exists so a repository cannot *"choose where a user's credentials are sent"*, and `permissions.<name>.network.proxy_url` does exactly that through a key the list does not cover.

### What was measured, and against what

The premise was verified at the consumer rather than inferred from the loader, using `codex doctor`'s effective-sandbox line in a trusted project directory (codex-cli 0.147.0):

| Project `.codex/config.toml` | Effective sandbox |
|---|---|
| empty | `restricted fs + restricted network` |
| `default_permissions = "p"` with `[permissions.p.network] enabled = true` | `restricted fs + **enabled network**` |
| the same with `enabled = false` | `restricted fs + restricted network` |
| `default_permissions` naming a profile nobody defines | the whole config fails to load |
| a profile whose only content is `extends` of a permissive parent | `restricted fs + **enabled network**` |

Three things follow, and each shapes the rule:

1. `enabled` is the field that decides. `mode` (`limited` / `full`) refines what an enabled network may reach; both values report as enabled, so `mode` alone is not the trigger.
2. `enabled = false` is a **denial**, not an absent field, which is why the parser keeps it as a pointer.
3. `extends` genuinely inherits, so a profile cannot be judged from its own table. cfgaudit walks the chain and names the inherited profile in the finding.

### Only a profile that is actually reached

cfgaudit reports the profile `default_permissions` selects, plus whatever that one inherits. A dormant profile definition nobody selects is **not** a finding, the same restraint that keeps `[sandbox_workspace_write]` inert under an explicit `read-only` mode. A `:`-prefixed built-in is not resolved from the file and is not reported either.

Under `danger-full-access` the network finding is suppressed as redundant: the sandbox is already off, and saying so twice is noise. The proxy and unix-socket findings still stand, because where traffic is routed is a different statement from whether it is allowed.

The `network.mitm` sub-table (`actions`, `hooks`) is **not** covered here. It carries command content and belongs in the command-content family, which needs its own plumbing and its own probe.

## Where cfgaudit looks

Codex config is **project-merged**, not user-global. Besides the user file it loads a repo-local `.codex/config.toml` — upstream resolves it both at the git root and by walking parent directories (`codex-rs/config/src/loader/mod.rs`, layer order `cwd` → `tree` → `repo`).

cfgaudit therefore scans:

| Path | Scope | Flag |
|---|---|---|
| `<repo>/.codex/config.toml` | project | always |
| `~/.codex/config.toml` (`$CODEX_HOME`) | user | `--user` |

**A committed `.codex/config.toml` is the case this rule exists for**, and it is the one cfgaudit missed until #388 — the rule was correct but only ever looked at the user file.

The bare `${PWD}/config.toml` layer is deliberately not scanned: the filename is too generic (Hugo, Zola and others use it), so decoding every repo's `config.toml` as Codex config would turn an unrelated file into a scan error for no coverage gain.

### Keys Codex refuses from a project layer

Upstream guards a subset against repo contents (`PROJECT_LOCAL_CONFIG_DENYLIST`), commented *"Project-local config comes from repository contents, so it should not get to choose where a user's credentials are sent or which local commands are run."* It covers `openai_base_url`, `chatgpt_base_url`, `apps_mcp_product_sku`, `responses_api_metadata`, `model_provider(s)`, `notify`, `profile(s)`, the two experimental realtime URLs, and `otel`, plus a special case that strips `features.respect_system_proxy`.

cfgaudit drops those from a project file so it never reports configuration the CLI ignores — this is why a committed `notify` is not treated as a command site and a committed `chatgpt_base_url` does not trigger CFG071.

`approval_policy`, `sandbox_mode`, `mcp_servers`, `default_permissions` and `permissions` are **not** on that denylist, which is exactly why they are worth flagging in a committed file.

### Trust gate

Project layers are *"loaded but disabled when the directory is untrusted"*. That is a real mitigation, and the same one CFG086 records for Cursor's workspace trust — and the same reasoning applies: trust is granted once, often reflexively, and thereafter every clone is covered. It caps the blast radius; it is not a reason to leave the setting in the repository.

The gate was measured rather than assumed, and it applies to the whole project layer rather than to permission profiles specifically: a deliberately malformed project `config.toml` stays silent until the directory carries `trust_level = "trusted"`, at which point its parse error surfaces. So permission profiles sit behind exactly the same precondition `sandbox_mode` and `approval_policy` already do, and no extra gate of the kind Codex applies to hooks was found in front of them.

## Trigger example

```toml
sandbox_mode = "danger-full-access"
```

→ `error`. And, under workspace-write:

```toml
[sandbox_workspace_write]
network_access = true
writable_roots = ["/home/dev/.ssh", "/etc", "/srv/artifacts"]
```

→ `error` (network), `error` (credential path), `error` (system path), `warn` (`/srv/artifacts`).

And through the profile mechanism, which needs no `sandbox_mode` at all:

```toml
default_permissions = "ci"

[permissions.ci]
extends = "base"

[permissions.base.network]
enabled = true
mode = "full"
proxy_url = "http://proxy.internal.example:8080"
dangerously_allow_non_loopback_proxy = true
```

→ three `error`s, each naming `base` as the profile `ci` inherits from.

## Safe alternative

```toml
sandbox_mode = "workspace-write"

[sandbox_workspace_write]
writable_roots = ["./build-cache"]
```
