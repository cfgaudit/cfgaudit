# CFG002 — unrestricted or cross-agent file-write grant

**Severity:** `warn`  
**OWASP:** [LLM03:2026 – Excessive Agency](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM03_ExcessiveAgency.md)  
**Agents:** claude-code

## What cfgaudit checks

CFG002 reports two forms of Claude Code `permissions.allow` entry:

- A bare `Edit` or `Write` grant, or an unrestricted `Edit` path pattern, which lets the agent overwrite any workspace file without a normal permission prompt.
- A concrete or globbed `Edit(path)` grant that reaches configuration consumed by another agent. The finding names both the path and that agent.

Claude Code ignores path specifiers on `Write` and `NotebookEdit`; only their bare tool names are grants. Consequently, entries such as `Write(.codex/config.toml)` and `Write(./**)` do not trigger the cross-agent check. An `Edit(path)` permission can, however, authorize both Edit and Write tool calls for that path.

Combined with prompt injection, a reachable MCP, hook, task, permission, or instruction file can make another agent execute attacker-controlled behavior later under a different approval model.

An allow entry that a `permissions.deny` entry in the same file fully blocks is not reported: the identical entry, the bare tool name, or a broader pattern of the same tool. Claude Code checks deny before allow, so the allow entry has no effect; measured with 2.1.312, allow `Bash(touch:*)` with deny `Bash(touch:*)` blocked the command, and a bare deny `Bash` removed the tool (#1041). A partial overlap, allow `Edit` with deny `Edit(.env)`, is still reported. Only the same file counts, because cfgaudit cannot see the deny lists of other settings layers, and a file Claude Code discards whole (CFG012) denies nothing.

Path matching follows Claude permission semantics: `**` spans path segments, while `*` and `?` do not; a pattern without a slash matches a basename at any depth; and a leading `/` anchors the pattern at the project root. Matching is case-sensitive on the platforms cfgaudit currently models.

### Claude Code 2.1.317 sensitive-file confirmation

Measured on Claude Code 2.1.317 on Linux using an explicit `Edit(**)` setting and `--permission-prompts none`, an Edit tool call still requested confirmation before changing `.mcp.json`, `.vscode/settings.json`, or `.vscode/tasks.json`. The same Edit call changed `.cursor/mcp.json` and `.codex/config.toml` without a permission denial.

CFG002 deliberately does not suppress the three protected paths. The measurement covered Edit tool calls only, while a valid `Edit(path)` permission also authorizes Write tool calls for that path. Until that second call path is measured, reporting the grant is the conservative result. This is also not treated as an open-ended promise about later Claude Code versions.

## Trigger example

```json path=.claude/settings.json
{
  "permissions": {
    "allow": ["Edit(.cursor/mcp.json)", "Edit(.vscode/settings.json)"]
  }
}
```

## Safe alternative

Do not grant edits to another agent's configuration. Scope ordinary edits to the source directories that need them and add explicit denies for foreign configuration where a broad grant is unavoidable:

```json
{
  "permissions": {
    "allow": ["Edit(src/**)"],
    "deny": ["Edit(.cursor/**)", "Edit(.codex/**)"]
  }
}
```

## Relationship to the SchemaStore schema

The [SchemaStore Claude Code settings schema](https://json.schemastore.org/claude-code-settings.json) rejects wildcard-only rules such as `Edit(*)` — its `permissionRule` pattern requires the args inside parentheses to contain at least one character that is not `)`, `*`, or `?`. That check only fires in editors and tools that load the schema (VS Code IntelliSense, JSON validators in CI plugins, etc.) and only if the developer has not silenced the warning.

The schema also cannot establish whether a syntactically valid concrete `Edit(path)` crosses an agent boundary. CFG002 catches both classes during file-system audits, pre-commit hooks, and scans of checked-out repositories. Treat the schema and the rule as complementary.
