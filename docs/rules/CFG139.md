# CFG139: a Kimi Code local.toml removes approval prompts or adds an outside folder

**Severity:** `error` (an allow that skips the sensitive-file prompt) · `warn` (an allow on a privileged or network command) · `info` (`additional_dir` outside the repository)
**OWASP:** [LLM03:2026 – Excessive Agency](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM03_ExcessiveAgency.md)
**Agents:** kimi-code

## What cfgaudit checks

Kimi Code 2.6.0 reads a project file, `.kimi-code/local.toml`, with two parts that change what the agent may do ([#1638](https://github.com/cfgaudit/cfgaudit/issues/1638)). The vendor docs recommend keeping the file out of Git, because it holds machine-specific settings; a committed copy applies to everyone who opens the repository.

### `[[permission.rules]]`

```toml
[[permission.rules]]
decision = "allow"
pattern = "Read"
```

Project rules are loaded for a trusted local workspace. Kimi Code evaluates its permission policies in this order: deny rules, the dangerous-command guard, ask rules, **allow rules**, the sensitive-file guard (`.env`, SSH keys, `credentials`), the git-control-path guard. An allow rule that matches a call therefore approves it before either guard asks. The dangerous-command guard and deny rules still run first.

| Allow rule | Severity |
|---|---|
| `Read`, `Write`, `Edit`, `Bash` or `*` with no argument pattern, or with one that constrains nothing (`Bash(*)`, `Edit(**)`) | `error` |
| one of those tools with a pattern that names a guarded file: `.env` and its variants, `id_rsa`, `id_ed25519`, `id_ecdsa`, `credentials`, `.ssh`, `.aws`, `.git` (`Read(**/.env)`, `Write(.git/hooks/*)`) | `error` |
| `Bash` on a privileged or network command: `sudo`, `su`, `doas`, `rm`, `chmod`, `chown`, `docker`, `curl`, `wget`, `ssh`, `scp`, `nc`, `ncat` | `warn` |

`Read`, `Grep` and `Glob` are approved without a prompt anyway, so `allow = "Read"` does only one thing: it removes the prompt before the agent reads `.env` or an SSH key.

### `[workspace] additional_dir`

A legacy field in 2.6.0: Kimi Code adds each listed folder to the workspace of an implicit (terminal) session once the folder is trusted, and loads the skills in it. Every entry that leaves the repository (an absolute path, a `~` path, a relative path above the root) is `info`. cfgaudit does not scan those folders.

## Not flagged

- `deny` and `ask` rules, which narrow.
- Allow rules with an argument pattern that names no guarded file (`Bash(npm test*)`, `Read(src/**)`), and `.env.example`, `.env.sample` and `.env.template`, which the guard exempts.
- Allow rules on other tools (`Grep`, `WebSearch`).
- `additional_dir` entries inside the repository.

## Trigger example

```toml path=.kimi-code/local.toml
[[permission.rules]]
decision = "allow"
pattern = "Bash"
```

→ `error`: `Bash` asks by default, and this rule approves every shell command that is not on the dangerous-command list.

## Safe alternative

Keep `.kimi-code/local.toml` out of Git, as the vendor docs recommend. Put shared rules that narrow (`deny`, `ask`) in the file if the team wants them, and narrow allow rules to the commands the project needs (`Bash(npm test*)`).

## Measurement

Read from the Kimi Code 2.6.0 source (`ProjectPermissionRulesService`, `AgentPermissionPolicyService`, `FileProjectLocalConfigService`) and the configuration docs of that release. On the 25,100-repository corpus, 2 repositories commit a `.kimi-code/` folder and none a `local.toml`, so the rule has no finding there yet. Whether an allow rule removes the prompt has not been measured on a live session, which needs a Kimi account (#1638, `needs measurement`).
