# CFG142: an MCP server, hook or task starts a container that reaches the host

**Severity:** `error` (the container can take over the host or read the reader's credentials) · `warn` (it shares a host namespace or loses a protection)
**OWASP:** [LLM03:2026 – Excessive Agency](https://github.com/GenAI-Security-Project/GenAI-LLM-Top10/blob/main/2026/final/LLM03_ExcessiveAgency.md)
**OWASP MCP:** [MCP02:2025 – Privilege Escalation via Scope Creep](https://owasp.org/www-project-mcp-top-10/) — provisional (MCP Top 10 v0.1)
**Agents:** claude-code, cline, codex, continue, copilot, cursor, devin, devin-desktop, gemini-cli, goose, grok, junie, kimi-code, opencode, qwen-code, roo-code, vscode, zed

## What cfgaudit checks

MCP servers are often started as containers (`"command": "docker", "args": ["run", "-i", "--rm", "mcp/<name>"]`), and hooks and tasks start containers too. A container is only a boundary as long as its `docker run` options keep it one. A committed configuration can add an option that hands the host to the container, and with it to whatever the image or the server inside it does, on the machine of whoever opens the repository ([#1682](https://github.com/cfgaudit/cfgaudit/issues/1682)).

CFG142 reads `docker run`, `docker container run`, `docker create` and `podman run` in:

- each MCP server launch, in every agent's MCP configuration;
- each command site: hooks, helpers, status lines and skill or command `!` blocks;
- each VS Code task, whether it runs on folder open or when the user starts it.

Only the options before the image count. What follows the image is the program's own command line.

| Option | What it gives the container | Severity |
|---|---|---|
| `--privileged` | every device and capability of the host | `error` |
| `-v` / `--volume` / `--mount` of `docker.sock`, `podman.sock` or the `docker_engine` pipe | the host's container daemon, which is root on the host | `error` |
| `--cap-add ALL`, `--cap-add SYS_ADMIN` | mount and most other kernel operations | `error` |
| `--pid host` | every process of the host | `error` |
| a mount of `/`, a drive root, `/etc` or `/root` | the host's file system or system configuration | `error` |
| a mount of the home directory (`~`, `$HOME`, `/home/<user>`, `/Users/<user>`, `C:\Users\<user>`, `%USERPROFILE%`) | everything the reader keeps there | `error` |
| a mount of a credential folder under it (`.ssh`, `.aws`, `.azure`, `.kube`, `.docker`, `.gnupg`, `.config` as a whole, `.config/gcloud`, `.config/gh`, `.npmrc`, `.netrc`, `.git-credentials`, `.pypirc`, `.claude`, `.codex`, `.gemini`) | the reader's keys and tokens, also read-only | `error` |
| `--network host` / `--net host` | the host's network, including services bound to localhost | `warn` |
| `--ipc`, `--uts`, `--userns` or `--cgroupns host` | a namespace of the host | `warn` |
| `--cap-add SYS_PTRACE`, `SYS_MODULE`, `NET_ADMIN`, `SYS_RAWIO`, `DAC_READ_SEARCH`, `BPF` | a kernel power that reaches past the container | `warn` |
| `--security-opt seccomp=unconfined`, `apparmor=unconfined`, `systempaths=unconfined`, `label=disable` | no syscall filter or mandatory access control | `warn` |
| a mount of `/proc`, `/sys`, `/dev`, `/boot`, `/run` or `/var/run` | a kernel or system folder of the host | `warn` |

One finding per command lists every option it found, at the highest severity among them.

**Not reported:**

- a container without these options: `docker run -i --rm mcp/x:1.0`;
- a mount of a folder inside the repository or a named volume: `-v ./data:/data`, `-v "$CLAUDE_PROJECT_DIR:/src"`, `-v ${workspaceFolder}:/workspace`, `-v $(pwd):/src`, `-v mcp-data:/data`;
- a mount of another folder under the home directory (`~/projects/site`, `~/.config/myapp`) or of `/tmp`;
- a capability Docker grants anyway or that reaches nothing past the container (`NET_BIND_SERVICE`, `CHOWN`), and `--cap-drop`;
- `--privileged=false`, `--network bridge`, `--security-opt no-new-privileges`;
- options after the image, and `docker` in prose or in an `echo`.

A sandbox that lets the agent reach `docker.sock` (`allowUnixSockets`) is [CFG022](CFG022.md); a broad path handed to an MCP server as an argument is [CFG076](CFG076.md); `DOCKER_HOST` pointed off the machine is [CFG082](CFG082.md). glsec reports the same options in CI scripts (GL054 to GL061, GL076, GL077), where they run on a CI runner, not on a developer's machine.

## Trigger example

```json path=.mcp.json
{
  "mcpServers": {
    "ops": {
      "command": "docker",
      "args": ["run", "-i", "--rm", "-v", "/var/run/docker.sock:/var/run/docker.sock", "-v", "~/.aws:/root/.aws:ro", "ghcr.io/example/ops-mcp"]
    }
  }
}
```

```text
[error] CFG142: mcpServers.ops command starts a container with "-v /var/run/docker.sock:/var/run/docker.sock" (the host's container daemon, which is root on the host), "-v ~/.aws:/root/.aws:ro" (the credentials in ~/.aws of whoever opens the repository). The container runs on the machine of whoever opens the repository, and whatever the image or the server inside it does reaches the host through these flags. Remove them; mount only a folder inside the repository, and add a capability or a host namespace only for a container you build and review yourself
```

## Measured

On 25,100 corpus repositories (20,130 popular, 4,970 low-star), CFG142 gives 15 findings in 9 files of 6 repositories, all `warn` and all `--network host`:

- 9 MCP server launches in 6 files (`.mcp.json`, `.cursor/mcp.json`, `.vscode/mcp.json`, `opencode.json`): Grafana, Postgres, MySQL, Redis and Drupal servers that reach a service on the developer's localhost.
- 6 VS Code tasks in 2 files, which install the project in a container on the host network.

No agent configuration in the corpus starts a container with `--privileged`, a Docker socket, a capability or a credential mount. The other agent configurations that name `docker.sock` or `--privileged` use them as a sandbox socket, a permission rule or `DOCKER_HOST`, not as a `docker run` option.

## Fix

Remove the option. Mount only a folder inside the repository, pass credentials as environment variables the user sets, and reach a local service through a published port instead of the host network. If the server really needs more, build the image yourself and document why.
