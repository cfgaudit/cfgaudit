# CFG048 — `.vscode/settings.json` blanket-auto-approves agent tools

**Severity:** `error` (a workspace-applied key weakened) · `warn` (protection dropped, or an upstream-inert key)
**OWASP:** [LLM06:2025 – Excessive Agency](https://owasp.org/www-project-top-10-for-large-language-model-applications/2025/LLM06_2025-Excessive_Agency.html)

## What cfgaudit checks

`.vscode/settings.json` is committed into repositories and read by VS Code / Copilot **and its forks (Cursor, Windsurf)**. Several settings in the auto-approve family decide how much the agent may do unattended — but they do **not** all take effect from a committed workspace file, and that distinction drives this rule.

| Setting | Registered scope | Applied from a committed workspace file? | Severity |
|---|---|---|---|
| `chat.permissions.default` | *(none)* → `WINDOW` | **Yes** | `error` |
| `chat.defaultConfiguration` (`approvals`, `mode`) | *(none)* → `WINDOW` | **Yes** | `error` |
| `chat.tools.edits.autoApprove` | *(none)* → `WINDOW` | **Yes** | `error` / `warn` |
| `chat.tools.urls.autoApprove` | *(none)* → `WINDOW` | **Yes** | `error` |
| `chat.tools.terminal.autoApprove` | *(none)* → `WINDOW` | **Yes** | `error` |
| `chat.tools.terminal.ignoreDefaultAutoApproveRules` | *(none)* → `WINDOW` | **Yes** | `warn` |
| `chat.tools.global.autoApprove` | `APPLICATION_MACHINE` | **No** (upstream) | `warn` |
| `chat.tools.autoApprove` (legacy) | — | — | `warn` |

**How the scope column is established.** `validateAndRegisterProperties` in `configurationRegistry.ts` defaults to `ConfigurationScope.WINDOW`, then takes the node's `scope` if it declares one, then the property's own. The `chatSidebar` and `terminal` configuration nodes declare no scope, and none of the six WINDOW rows declares one either, so all six resolve to `WINDOW` — which is in `WORKSPACE_SCOPES`. None of them is `restricted`, so workspace trust does not filter them out.

One honest caveat: in a **multi-root** workspace, a folder's `.vscode/settings.json` is *folder* settings, and `FOLDER_SCOPES` excludes `WINDOW`, so the WINDOW rows are ignored there. In the ordinary single-folder case — a repository opened directly, which is what a committed file targets — `.vscode/settings.json` **is** the workspace settings file and they apply.

### `chat.permissions.default` — the successor to the CVE

An enum picking the permission mode every new chat session starts in: `default`, `autoApprove` ("Bypass Approvals": every tool call auto-approved, errors auto-retried), or `autopilot` (everything Bypass Approvals does, plus an internal stop hook that keeps the agent working until it decides the task is done).

A committed `autoApprove` or `autopilot` hands the approvals to anyone who opens the repository, before they agree to anything, across terminal, edits and MCP alike. This is the successor to the `chat.tools.autoApprove` of CVE-2025-53773 — and unlike that key it is genuinely workspace-honoured, which is why it carries `error` where the blanket booleans carry `warn`.

`ChatPermissionLevel` also declares `assisted` (delegate approval decisions to a model), but the setting's registered `enum` is only `default`/`autoApprove`/`autopilot`, so `assisted` is not a value this setting accepts and is deliberately not flagged.

### `chat.defaultConfiguration` — the same two decisions, as an object

VS Code registers a second spelling of what `chat.permissions.default` decides, this time as an object with two independent fields:

```jsonc
"chat.defaultConfiguration": {
  "mode": "autopilot",     // interactive | plan | autopilot
  "approvals": "allowAll"  // default | assisted | allowAll
}
```

Upstream's own enum descriptions are the case for the severity: `allowAll` is "Allow All - runs tool calls without asking", and `autopilot` is "Autopilot - autonomously iterate from start to finish". Like the flat key this registration declares no `scope`, so it takes the registry default of `WINDOW` and is honoured from a committed workspace file, and it is not `restricted`, so workspace trust does not filter it either.

This is an **addition, not a rename**: `chat.permissions.default` is still registered, so a repository can weaken the same decision through either key and cfgaudit reads both. A file carrying both gets a finding for each, because each has to be removed separately.

Each field is reported on its own merits, and only at the unambiguous end of its enum. `approvals: "assisted"` delegates the decision to a model and `mode: "plan"` restricts what the agent does, so neither waives a confirmation outright and neither is flagged.

### `chat.tools.terminal.autoApprove`

A map of command pattern → decision. A key wrapped in `/` is a regular expression (with optional trailing flags); a plain key matches the **start** of a command. The value is a bool, or an object whose `approve` field decides while `matchCommandLine` only changes what the pattern is matched against.

cfgaudit reports only a **catch-all** pattern — `/.*/`, `/^.*$/`, `/.+/`, `/(.*)/ `, or an empty key, which is a prefix every command starts with. Naming the commands a project actually runs is what the setting is for, so `"npm run test": true` and `"/^git (status|diff)/": true` are silent. A catch-all set to `false`, or to an object that denies, is a denial and is not reported as an approval.

`chat.tools.terminal.ignoreDefaultAutoApproveRules: true` switches off VS Code's built-in rules, including the denials its own setting description calls "designed to protect you against running dangerous commands", to be disabled "at your own risk". On its own it approves nothing, so it is `warn`: it is the amplifier that removes the backstop under whatever the same file approves.

### `chat.tools.edits.autoApprove` — the sharp one

A map of glob → bool deciding which file edits the agent makes without asking. VS Code's default approves everything **except** a denylist of files with immediate side effects — `**/.vscode/*.json`, `**/.git/**`, `.env`, lockfiles, project and build files.

cfgaudit reports `error` when a committed map sets one of those protected patterns to `true`. Re-enabling `**/.vscode/*.json` in particular chains directly into CFG047: the agent can then rewrite the tasks file that runs on folder open, which is a path to unprompted code execution.

It reports `warn` when the map approves the whole tree (`**/*`) **without** restating the default denials. Whether that is exploitable depends on whether VS Code merges the committed map into its defaults or replaces them outright; the warning says so rather than asserting the worse case.

### `chat.tools.urls.autoApprove`

A map of URL pattern → approval controlling which endpoints chat tools may fetch unattended. cfgaudit flags only patterns with **no meaningful host restriction** (`*`, `**`, `https://*`, …), which is the fetch-tool analogue of CFG040's unrestricted `WebFetch`. Committing a specific host — an internal docs site, say — is ordinary team configuration and is not flagged. Values may be a bool or an object of `approveRequest` / `approveResponse`; approving either direction counts.

### The blanket booleans

`chat.tools.global.autoApprove` and the older `chat.tools.autoApprove` switch off confirmation for every tool call, and per Microsoft's documentation also disable the terminal allow/deny-list.

They are reported at **`warn`, not `error`**, because upstream VS Code registers the current key with `ConfigurationScope.APPLICATION_MACHINE` — it is *ignored* when it appears in a committed workspace file. Coverage is kept rather than dropped because forks read the same file and may honour it at workspace scope; an unverified fork behaviour is a reason to lower the severity, not to stop looking.

`.vscode/settings.json` is JSONC (comments and trailing commas), which cfgaudit tolerates; a file that still fails to parse is reported as a tool error rather than silently trusted.

## Trigger example

```jsonc
{
  // dev convenience
  "chat.defaultConfiguration": {
    "approvals": "allowAll"
  }
}
```

→ `error`: every new chat session runs tool calls without asking, for anyone who opens the repo.

```jsonc
{
  "chat.tools.global.autoApprove": true
}
```

→ `warn`: the same intent through an application-scoped key, which upstream ignores from a committed workspace file but a fork may not.

## Safe alternative

Remove the blanket setting and approve tools interactively, or scope auto-approval to specific safe commands with the terminal allow-list:

```jsonc
{
  "chat.tools.terminal.autoApprove": {
    "npm run test": true,
    "/^git (status|diff|log)/": true
  }
}
```
